# 평가 질의 만드는 방법 A~D

평가셋은 **질의**와 **정답 조문** 한 세트로 이루어집니다. 질의는 아래 네 가지 소스(A~D) 중 하나로 만들고, 소스를 바꾸거나 섞어 쓸 수 있습니다. 정답은 소스와 관계없이 **같은 방식**으로 정합니다. 검색 결과를 모아 후보를 만들고(pool), 후보마다 등급을 판정합니다(judge).

소스마다 다른 것은 두 가지뿐입니다.

- 질의를 어디서 어떻게 얻는가
- 처음부터 정답 후보(seed)가 있는가

해석례 같은 질의응답 데이터가 없는 프로젝트에서도 B~D와 공통 정답 단계만으로 같은 체계를 쓸 수 있습니다.

## A. 기존 질의응답 데이터 (예: 법령해석례)

- **방법:** 질의와 근거가 함께 있는 공개 자료를 가져옵니다.
  - 질문 원문은 그대로 쓰지 않고 사용자 말투(`user`)와 전문가 말투(`expert`)로 다시 씁니다.
  - 법령명, 조문 번호, 원문 구절이 질의에 새지 않았는지 유출 검사를 합니다.
- **seed:** 있음. 자료가 인용한 조문입니다(핵심 인용 2등급, 부수 인용 1등급).
- **장점:** 실제 쟁점이고 전문가가 확인한 근거가 있어 정답 신뢰도가 가장 높습니다.
- **단점:**
  - 자료의 분포를 따라갑니다. 해석례는 행정·기관 쟁점에 치우칩니다.
  - 인용되지 않은 적절한 조문은 놓칩니다.
- **lawlens:** 주력. `build_expc.py`, `rewrite_expc.py`. 180건(360문항)이 `eval/datasets/expc_rewrite.jsonl`에, 판정한 정답은 `expc_rewrite.judged.jsonl`(조정용 `.dev` · 최종 확인용 `.test`)에 있습니다.

## B. 문서 → 질문 (조문을 보고 질문 생성)

- **방법:** 조문을 표본으로 뽑고, LLM이나 사람이 그 조문으로 답할 수 있는 질문을 만듭니다.
- **seed:** 있음. 출발한 조문이 seed입니다.
- **장점:** 자동화가 쉽고 법령 종류(법률·시행령·시행규칙)를 고르게 덮을 수 있습니다.
- **단점:**
  - 조문 표현이 질문에 묻어나 점수가 부풀기 쉽습니다.
  - 실제 사용자 질문과 거리가 있습니다.
- **lawlens:** 진단용으로 작게만 씁니다. `build_synth.py`.

## C. 상황 시나리오 먼저 (조문을 보지 않고 질문 생성)

- **방법:** 주제 목록(전세, 퇴직금, 교통사고 등)과 사용자 유형을 정하고, 조문을 보지 않은 채 실제 겪을 법한 상황 질문을 씁니다.
- **seed:** 없음. 정답은 전적으로 pool + judge로 정합니다.
- **장점:**
  - 실제 사용 분포에 가장 가깝습니다.
  - 질문 쓰는 사람이 정답 표현을 보지 않으므로 유출이 없습니다.
- **단점:** pool 편향이 생깁니다. 현재 검색기가 못 찾은 정답은 판정 대상에 들지 않습니다.
  - 대책: 질의를 바꿔 쓴 검색과 법령명 검색 결과를 pool에 추가합니다.
- **lawlens:** A의 빈 곳(일상 질문)을 채우는 보완용입니다. 아직 생성기(`scenario.py`)가 없습니다.

## D. 실제 사용 로그

- **방법:** 서비스 검색 로그에서 질의를 표본 추출합니다. 개인정보를 걸러 내고 중복·무의미 질의를 지웁니다.
- **seed:** 기본은 없음. 클릭 기록이 있으면 약한 seed로 씁니다.
- **장점:** 진짜 사용자 분포입니다.
- **단점:**
  - 서비스를 연 뒤에만 쓸 수 있고, 개인정보 처리가 필요합니다.
  - C와 같은 pool 편향이 있습니다.
- **lawlens:** 아직 쓸 수 없습니다. 로그가 쌓이면 C를 점차 대체합니다.

## 한눈에 비교

| 소스 | 질의 출처 | seed | 현실성 | 정답 신뢰도 | 자동화 | lawlens 역할 |
|---|---|---|---|---|---|---|
| A 질의응답 데이터 | 해석례 등 | 있음 | 중 | 높음 | 중 | 주력 |
| B 문서→질문 | 조문 | 있음 | 낮음 | 중 | 높음 | 진단용 |
| C 상황 시나리오 | 주제 목록 | 없음 | 높음 | pool 의존 | 중 | 보완 |
| D 사용 로그 | 실제 사용자 | 약함/없음 | 가장 높음 | pool 의존 | 중 | 서비스를 연 뒤 |

## 공통 정답 단계 (모든 소스)

1. **Pool:** 질의마다 hybrid, dense, sparse 검색 결과 상위 20개의 합집합에 seed를 더합니다. C와 D는 추가 검색 결과도 넣습니다.
2. **Judge:** 후보 조문마다 등급을 매깁니다.
   - 등급: 2 핵심 / 1 관련 / 0 무관
   - LLM으로 판정하되, 일부는 사람이 매겨서 일치도(kappa)를 확인합니다.
   - 가능하면 서로 다른 계열의 판정기 두 개로 판정해 합칩니다. 같으면 그대로, 1 차이는 규칙으로, 0 ↔ 2는 사람이 정합니다.
3. **판정 단위:** 같은 상황에서 나온 질의(`user`/`expert`)는 판정 결과를 공유합니다.
4. **판정 안 된 문항:** 평가에서 뺍니다.

## 운영 원칙

- **점수는 소스별로 따로 봅니다.** 섞으면 B처럼 쉬운 셋이 평균을 끌어올립니다.
- **최종 확인용을 떼어 둡니다.** 소스마다 일부를 최종 확인용으로 떼어 두어, 튜닝이 평가셋에 맞춰지는 것을 막습니다.
- **비중은 주 사용자에 따라 정합니다.** 일반인이면 C, 실무자면 A를 늘립니다. 현재 잠정안은 A 6 : C 3 : B 1입니다.

## 규모와 진행 순서

### 몇 문항이면 되나

문항 수는 질의가 아니라 **상황(해석례 · 시나리오) 수**로 셉니다. 같은 상황의 `user`·`expert` 질의는 정답이 같고 결과도 함께 움직여서, 통계적으로는 1.5개 정도의 가치밖에 없습니다.

hit@10이 0.8 근처일 때 상황 수별 95% 신뢰구간(이항분포 근사)은 다음과 같습니다.

| 상황 수 | 오차 범위 | 구분할 수 있는 차이 |
|---|---|---|
| 50 (시범) | ±11%p | 아주 큰 차이만 |
| 100 | ±8%p | dense vs hybrid 같은 큰 차이 |
| 300 | ±4.5%p | 리랭커 도입 같은 중간 크기 개선 |
| 1,000 | ±2.5%p | 미세 튜닝 |

같은 문항으로 두 방식을 비교하면(대응 비교) 문항 간 난이도 차이가 상쇄되므로, 실제로는 이 표보다 작은 차이도 구분됩니다.

**목표: 상황 300개(질의 약 600개).**

| 소스 | 상황 수 | 질의 수 | 소스별 오차 |
|---|---|---|---|
| A 해석례 | 180 | 360 | ±6%p |
| C 상황 시나리오 | 90 | 180 | ±8%p |
| B 조문→질문 | 30 | 30~60 | 진단용, 참고만 |

이 중 3분의 1(100개)을 최종 확인용으로 떼어 둡니다.

판정량은 상황 하나당 후보 40~60개로 잡으면 12,000~18,000건입니다. 사람이 하기는 어렵고 API 판정이 현실적입니다. 정확한 숫자는 시범 pool로 확인합니다.

### 소스를 섞는 방법

- **파일:** 소스별로 따로 둡니다(`expc_rewrite.jsonl`, `scenario.jsonl`, `synth.jsonl`). 한 파일에 섞어 점수 하나로 보지 않습니다.
- **점수:** `run`에 함께 넣어 돌리면 리포트에 데이터셋별 점수가 나란히 나옵니다.
- **가중 평균:** 전체 점수가 필요하면 비율(예: A 6 : C 3 : B 1)로 가중 평균합니다.

### 진행 순서

1. **A 시범 50건에 pool + judge 적용:** 기존 seed와 사람 판정 샘플로 판정기를 검증합니다. seed가 있는 A에서 먼저 확인하는 이유는, 판정 기준이 틀렸을 때 다시 판정할 양이 가장 적기 때문입니다.
2. **A를 180건으로 확대:** 질의를 다시 쓰고 판정합니다. (완료. 아래 "A 판정 기록")
3. **C 생성기 만들기:** 90건을 만들고 같은 판정기로 정답을 붙입니다. C는 seed가 없어 판정기에 전적으로 의존하므로, 판정기를 검증한 뒤에 만듭니다.
4. **B와 A 300건 확대:** 필요하면 그때 합니다.

180건 결과와 300건 결과의 검색 방식 순위가 같으면 300건까지 가지 않고 멈춰도 됩니다. C의 비중은 3단계 전까지 주 사용자(일반인/실무자)를 정해 결정합니다.

### A 판정 기록

| 단계 | 판정기 | 근거 | 결과 |
|---|---|---|---|
| 1차 | Claude (대화 중 직접 판정) | 대부분 조문 제목, 일부 본문 앞부분 | `expc_rewrite.claude.judgments.jsonl` |
| 2차 | Codex CLI (gpt-6.1-sol, 추론 high) | 조문 전문 (최대 2,000자) | `expc_rewrite.codex.judgments.jsonl` |
| 합치기 | `judge-merge` (B = Codex) | 0 ↔ 2로 갈린 15개는 전문을 보고 직접 판정 | `expc_rewrite.judge_overrides.json` → `expc_rewrite.merged_answers.json` → `expc_rewrite.judged.jsonl` |

- 두 판정의 일치도: 후보 5,532개 중 일치율 0.937, kappa 0.688, 2차 가중 kappa 0.855, 관련/무관 kappa 0.760.
- 1차가 더 엄격했습니다(관련 이상 506개 대 711개). 근거가 얕아 시행령 · 시행규칙의 실제 기준 조문을 놓친 경우가 많았습니다.
- 두 정답으로 dev를 평가하면 검색 방식 순위가 같았습니다. 절대값은 판정기에 따라 0.03~0.05 움직입니다.
- 합친 결과: 같음 5,183 / seed라서 높은 쪽 99 / Codex 쪽 235 / 직접 판정 15. 1차에서 관련 조문이 없어 빠졌던 1건(340327)이 다시 들어가 180건(360문항)이 됐습니다.

## 참고 사례

A~D는 따로 이름 붙은 표준 분류가 아니라 이 프로젝트에서 정리한 구분입니다. 다만 각 방식과 공통 정답 단계는 연구와 실무에서 쓰는 방법에 대응합니다.

### 질의 소스별 사례

- **A 질의응답 데이터:** 법률 검색 벤치마크 대부분이 이 방식입니다.
  - [BSARD](https://ar5iv.labs.arxiv.org/html/2108.11792) (벨기에): 시민의 실제 법률 질문 1,100여 개에 법률 전문가가 관련 조문을 달았습니다. lawlens 해석례와 가장 비슷한 구조입니다.
  - COLIEE (일본 민법): 변호사 시험 문제를 질의로, 근거 조문을 정답으로 씁니다.
  - [STARD](https://aclanthology.org/2025.coling-main.50.pdf) (중국): 기존 벤치마크가 시험·판결문 같은 전문 질의에 치우쳤다는 문제를 지적하고 일반인 질의를 모았습니다. `user`/`expert`를 나눈 이유와 같은 문제의식입니다.
  - [LeCaRDv2](https://arxiv.org/pdf/2310.17609) (중국): 인용 관계만으로 정답을 정하는 방식은 성문법 체계에 맞지 않는다고 지적합니다. 인용 조문을 seed로만 쓰고 다시 판정하는 이유입니다.
- **B 문서→질문:** 원래는 학습 데이터용으로 많이 씁니다(InPars, Promptagator).
  - LLM이 만든 질의는 사람 질의보다 정답 문서와 어휘가 더 많이 겹칩니다([참고](https://www.arxiv.org/pdf/2501.14466)).
  - 합성 평가셋은 절대 점수를 왜곡할 수 있지만, 시스템끼리 비교하는 데는 영향이 작다는 보고가 있습니다([Rahmani et al., SIGIR 2024](https://arxiv.org/html/2405.07767v1), [SynDL](https://arxiv.org/pdf/2408.16312)).
- **C 상황 시나리오:** 정보 요구를 먼저 정하고 질의를 만드는 TREC식 주제 작성에 가깝습니다. C를 직접 다룬 자료는 아직 찾지 못했습니다.
- **D 실제 로그:** 실무에서는 1순위로 꼽습니다. 합성 질의는 실제 사용자 질의를 잘 대신하지 못하므로, 로그가 있으면 로그를 우선합니다([Vespa](https://blog.vespa.ai/improving-retrieval-with-llm-as-a-judge/)).

### 정답 정하기 (pool + judge) 사례

- **Pooling:** TREC의 오래된 표준입니다. 여러 검색 방식의 상위 k개를 섞어 후보를 만듭니다. 한 가지 방식만 쓰면 편향이 생깁니다.
- **LLM 판정:** [UMBRELA](https://arxiv.org/abs/2406.06519)가 TREC 2024 RAG 트랙의 301개 주제에 쓰였습니다. 사람이 전부 판정한 결과와 시스템 순위 일치도(Kendall's τ)가 0.86 이상이었습니다([Upadhyay](https://uwspace.uwaterloo.ca/items/4d18073e-d9b6-45e5-91b3-e530dd88dd5f)).
- **사람 보정:** 사람이 소량을 판정해 LLM 판정기를 맞추는 것이 권장 절차입니다. Vespa는 질의 26개, 판정 90건 정도로 보정했습니다.
- **알려진 한계:**
  - pool에 들지 않은 문서는 보통 무관(0)으로 처리되는데, 이것이 특정 검색 방식에 불리한 편향을 만든다는 지적이 있습니다.
  - LLM이 사람보다 관대하게 판정한다는 보고가 있습니다([참고](https://www.themoonlight.io/review/a-large-scale-study-of-relevance-assessments-with-large-language-models-an-initial-look)).

### 이 설계에 반영한 점

1. **점수 해석:** 점수는 검색 방식끼리 비교하는 데 쓰고, 절대값에 큰 의미를 두지 않습니다. 합성 질의(B·C)일수록 그렇습니다.
2. **판정기 보정:** 사람 판정 샘플로 확인할 때 1등급(관련)이 지나치게 많이 붙는지 특히 봅니다.
3. **pool 범위:** pool에 넣는 검색 방식은 다양할수록 좋습니다. 리랭커나 법령명 검색 결과가 생기면 pool에 추가합니다.
